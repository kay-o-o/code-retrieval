# mini-coding-agent 复现与改造记录

上游仓库：`rasbt/mini-coding-agent`，单文件 1019 行，一个能读写文件、跑 shell、
委派子智能体的最小 coding agent。

本项目在它的基础上做了三轮改造，每轮都先量一个数、再改、再量。

---

## 一、先把原生 function calling 接上

### 现象

直接跑原始代码，模型输出这样的东西：

```
<｜DSML｜  calls>
```

`parse()` 只认 `<tool>` 标签，看到这个就当成「格式错误」，重试到次数上限后
返回 `Stopped after reaching the step limit without a final answer`。
基线 10 道题通过 2 道。

### 原因

上游用**文本协议**教模型写字：prompt 里给几个 `<tool>{...}</tool>` 示例，
再用正则从回复里抓。这套约定在 2024 年的小模型上有效，现代模型不吃这套——
它们有自己的结构化 `tool_calls` 通道。

### 改法

- `OpenAICompatibleModelClient.complete()` 增加 `tools` 参数，把上游那套
  字符串 schema（`"str='.'"`、`"int=1"`）翻译成标准 JSON Schema，
  走 `tool_calls` 通道返回。
- `ask()` 优先读 `last_tool_calls`，没有结构化调用时再退回文本解析。

### 连带责任

文本协议有个副作用：模型只能输出 `<tool>` 或 `<final>`，**收口是被格式强制的**。
换成原生调用后，模型可以无限调工具，收口责任落回代码侧。

实测就是这样：接了原生通道后成功率只到 2/10，失败任务全是
`Stopped after reaching the step limit`，工具序列是 `search, search, run_shell, search...`
——模型在持续调工具，从不收尾。

### 强制收口

工具预算用完的那一轮，**不再传 `tools` 参数**，并追加一段指令要求立即作答：

```
Tool budget is exhausted. Answer the user now using what you already collected.
```

不传 tools 比在 prompt 里写「请停止调用工具」有效得多，因为后者只是建议，
前者拿掉了选项。

2/10 → 7/10。

## 二、把 search 从 grep 换成混合检索

### 现象

剩下 3 个失败任务有一个共同形状：**中文提问，英文标识符**。

| 题 | 期望 | 上游 search 的结果 |
|---|---|---|
| 工具返回内容超过多少字符截断 | `MAX_TOOL_OUTPUT = 4000` | `(no matches)` |
| read_file 一次最多读多少行 | `int=200` | `(no matches)` |

上游 `search` 是 `pattern.lower() in line.lower()`。问句里没有 `MAX_TOOL_OUTPUT`
这个串，就永远匹配不到。模型拿不到结果，继续换词再搜，把步数烧完。

### 改法：`code_index.py`

零第三方依赖（`urllib` 发请求、`math` 算余弦），三件事：

1. **切块**：按空行切，26 行左右，带 6 行重叠。首次切分从中点开始找空行，
   会把函数切碎、把答案挤出 top-3，改成从 2/3 处开始找。
2. **两路排序**：BM25（英文标识符 + 中文 unigram/bigram）负责符号名，
   向量（`text-embedding-v3`，1024 维）负责换个说法的问句。
3. **加权 RRF 融合**。

### 上下文头

代码块有个天然弱点：`MAX_TOOL_OUTPUT = 4000` 这一行本身没有语义，
换个语言问就匹配不上。给每块补一行头再送去向量化：

```
文件 mini_coding_agent.py › def clip
```

T08 的目标块从第 33 名进到 top-3。

### 上下文头不能只取第一行

带 6 行重叠，块的开头常常是**上一个函数的尾巴**。`read_file` 的 schema 块
开头是 `def remember` 的残余，上下文头就写成了 `def remember`——
问「read_file 最多读多少行」时，这块连 top-5 都进不去（T06 失败）。

改成列出块内覆盖的**所有**符号：

```
文件 mini_coding_agent.py › def remember / def build_tools
```

T06 恢复。

### RRF 的 k 不是通用常数

k=60 来自 web 规模语料。146 个块的时候，`1/(60+rank)` 把所有名次压成几乎
一样的权重，正确答案被稀释。

在 11 条用例上重扫：k=10、权重 0.8/0.2 时 R@3 36.4% / MRR 0.276，
k=3 的 0.5/0.5 是 27.3% / 0.200。

### 定义优先

两路排序有个共同的偏见：**提到某个标识符的块，排在定义它的块前面**。

查 `tool_write_file`，BM25 返回的是工具 schema 里列出这个名字的条目，
向量返回的也是 schema。真正该看的 `def tool_write_file` 在后面。

人 grepping 会直接跳定义，排序器也该有这个先验。加一条规则：块内出现
`def X` / `class X` / `X =` / `"X":` 这类定义行，按次数加分。

R@1 从 9.1% 翻到 18.2%，MRR 0.276 → 0.294。

## 三、评测本身修了三次

这一节是最该写的，因为三次都是**量错了**，不是代码错了。

### 1. 评测脚本污染索引

第一版把 10 道题内联在 `scripts/eval_baseline.py` 里。脚本本身被索引了，
而且语义上和题目完全一致（题目就在里面），BM25 直接排第一——
模型读的是评测脚本，不是源码。

修法：题目抽到 `eval/tasks.json`，**描述语料的东西必须放在语料外**。

### 2. 黄金行号会过期

`eval/retrieval_cases.json` 第一版存的是 `path:line`。源码涨了 300 行之后，
行号全错位，但脚本不报错——它继续拿旧行号去比对，11 条用例全部悄悄失效。
混合检索 R@3 读出 18.2%，看起来像「改造把检索搞坏了」，其实是尺子断了。

修法：gold 存**锚点字符串**（`"def tool_run_shell"`），运行时解析成行号。
找不到锚点直接报错退出，不再静默算错。

### 3. 评测没有跑生产代码

`orders()` 里复制了一份 RRF 融合逻辑，但没带上生产代码里的 `_rare_terms`
精确加分。表里的数字不是模型实际会看到的排序。

修法：`hybrid` 直接调 `index.search()`。

> 一个测 x 的基准，如果自己重写了一遍 x，那它测的是自己。

### 4. 排名靠后的块压根没展示

`format_hits()` 遇到字符预算就 `break`，5 个命中只显示前 2 个。
top-1 排错的时候，正确答案在 rank 4 也永远看不到。

改成按剩余块数分摊预算，每块窗口变短，但 5 块都能露头。

## 四、答案被截断也算失败

修完检索，T10 还是不过。但失败形态变了：模型已经找到了 `parse` 和主循环
的两条路径，回答却在 `调用 json.load` 处**断句**——被 512 的 `max_new_tokens`
截掉了。

工具调用轮输出很短，512 够用；只有最终作答需要成段输出。给作答轮单独设
下限（1024），并在 `finish_reason == "length"` 时翻倍重试一次。

T10 通过，10/10。

## 六、这些数字的边界

1. **10 道题是我自己出的，且都在仓库内。** 100% 说明「同类问题上这套改动有效」，
   不说明「通用代码问答达到 100%」。真正有说服力的是 20% → 100% 的变化幅度，
   不是终值。
2. **R@3 36.4% 不算高。** 但这个数字和端到端 90%+ 并不矛盾：agent 是多跳的，
   搜一次不全中，读一次文件就补上了。检索指标衡量的是「一次找对」，
   不是「最终答对」。
3. **11 条用例不足以支撑精细调参。** 权重和 k 是在同一批用例上选的，
   有过拟合风险。要更硬，需要另建一份 holdout。
4. **没测过的**：`run_shell` 的风险分级、`delegate` 在深层任务上的表现、
   超过 50 个文件的大仓库。
